# Nordic

多平台 NAS 音乐播放器。连接你自己的音乐服务器,在任意设备上听自己的库。

- **音源**:Navidrome、Subsonic / OpenSubsonic、飞牛音乐(fnOS)
- **多线路**:同一个音乐库可配多条地址,自动测速择优,线路故障自动切换
- **转码播放**:按网络情况选择原始音质或转码码率
- **离线下载**:整张专辑 / 单曲 / 一位艺人的歌拉到本机(原文件,不转码),
  进度与失败原因都是真的;已下好的曲子播放时走本机文件,**封面也用本机那张**,
  断网也能听、也能看。断网时库刷不出来,但「设置 → 下载管理」里点开已下好的
  条目就能直接播 —— 曲目清单随下载记录一起存在本机
- **歌单管理**:新建 / 重命名 / 删除,把歌加进歌单,从歌单里按位置移除
- **排序**:专辑与歌曲两栏各一套口径 —— 专辑走服务器(Navidrome 的「最近添加 /
  最近播放 / 常听」本地算不出来),歌曲在本地排(标题 / 艺人 / 专辑 / 添加时间)
- **缓存**:音乐库列表落盘一份,启动先铺出来再静默刷新(不必空等一次全量拉取);
  刷新失败时留在屏幕上并说明一句是什么时候同步的 —— 断网也还有东西可看。
  封面走磁盘缓存(按封面 id + 尺寸作键,不按 URL —— Subsonic 每次请求换 salt)。
  **听过的歌也留一份**(边听边写,不多花一份流量),再听直接读本机、断网也能放;
  上限在设置里选(不缓存 / 256 MB … 4 GB,默认 1 GB),满了按「最久没听」淘汰。
  缓存**只管缓存**:点名下载的那些在另一个目录里,永远不会被淘汰掉
- **平台**:Android、iOS、Windows、macOS、Linux、Web(单一 Flutter 代码库)

## 当前阶段:M2 — Android 客户端

原型已确认,开发已开始。`prototype/` 是**唯一的设计真相来源**,原样保留作对照基准;
应用是它的逐项实现,并接上了真实的 Subsonic 协议。

```
lib/
  theme/      设计 token(styles.css :root 的 Dart 翻译)、强调色取色、玻璃、氛围背景
  data/       Subsonic 协议:鉴权、客户端(多线路择优 + 故障切换)、映射、配置
              以及下载:落盘索引(download_store)、下载器(download_manager)、网络探针
              缓存:音乐库快照(library_cache)、听过的歌(media_cache)与文件命名规则
              (media_files)、排序口径(sorting)
  playback/   just_audio + audio_service:队列、四档转码、通知栏 / 锁屏控制、
              播放源选取(本机有下载 / 缓存就走本机文件)、边听边缓存
  state/      应用级状态:连接、音乐库、收藏、偏好、下载、缓存
  ui/         shell(主壳 / 播放坞 / 标签栏)、screens(21 屏)、widgets(共享组件)

tool/build.sh 是构建入口 —— 它设好引擎产物镜像再调 flutter
```

界面已覆盖原型全部 21 屏:

> 服务器与线路 → 首页(正在播放 / 最近添加 / 最近播放 / 最常播放)→
> 音乐库(专辑 / 艺人 / 歌曲 / 歌单)→ 专辑详情 → 艺人详情 →
> 播放页 → 转码质量 → 播放队列 → 线路切换 → 歌词 → 搜索 → 设置 →
> 下载管理 → 新建歌单 → 添加线路 → 上下文菜单 → 歌单详情(含增删改)

设计板上还有第 22 格 —— **应用图标**:它不对应应用里的任何一屏,是「这个应用在启动器里
长什么样」的设计交付物,候选、定稿的三档尺寸(48px 是判据)、启动器四种遮罩各摆一份。
图形来自 `tool/app_icon.py`,和落到 Android 资源里的 PNG 是同一次生成的同一份矢量 ——
所以要改几何改那个脚本,别改 `prototype/icon.js`。

**底栏是「首页 / 音乐库 / 设置」**(2026-10-17 起,原型与应用同步):搜索是
「知道要找什么」时的动作,用完就退,占一个常驻位置不划算 —— 它挪进首页与音乐库
顶栏那颗放大镜,变成**推入的页面**;空出来的位置给首页,「不知道听什么」时才需要
一个一直能回的地方。首页铺的是**服务器口径**的三条货架(正在播放 / 最近添加 /
最近播放 / 最常播放),音乐库只管「库里有什么」—— 两屏的分工就这一条线。

### 界面改动一律**先改原型**

`prototype/` 是唯一的设计真相来源,这不是修辞:**任何界面 / 交互的增删改,先改
`prototype/`**(`app.js` 的屏幕函数 + `styles.css`、新屏幕要进 `VIEWS` 与 `BOARD`),
定下来之后应用再去实现。**不要在应用里「顺手」做一个原型里没有的东西** ——
设计板不再能对照、别人无从知道那个东西本来该长什么样,而用户是真的会去看原型的。

> 这一条是 2026-10-17 立的:当时加首页 tab 直接改了应用、没动原型,被指出来了。
> 补做时连带修掉一个漏网的重复:那次只把「继续收听」与「最近添加」加到了首页,
> **没从音乐库撤掉**,于是两屏各铺了一份。同一天还补了首页那屏漏掉的**底部托盘** ——
> 它是从音乐库那两栏搬过来的,搬的时候没带上 `bottom()`,于是首页没有路去别的地方。」

顺带记一条自检习惯:改完原型跑一遍 `.tmp-shots/*.cjs` 里的 playwright 脚本
(见那儿已有的模板),顺手看控制台 —— 那次改动里漏掉的 `pct` 引用,
就是靠它报的 `Uncaught ReferenceError` 抓到的。

### 构建

**统一走 `tool/build.sh`**,不要直接跑 `flutter build`:

```bash
tool/build.sh            # debug APK
tool/build.sh release    # release APK
tool/build.sh run        # 在设备上跑
```

侧载用的 release 包由这个脚本**落成标准名字**:

```
build/dist/Nordic-1.0.17+18-release.apk
             └ 应用  └ pubspec 的版本
```

默认那个 `app-release.apk` 装上手机、发给别人之后分不清是哪一版,连「是哪个应用」
都得点开看。版本号**只从 `pubspec.yaml` 读**,不另存一份;脚本还会顺手校验
签名、包名与包内 `versionName` 是否真与 pubspec 对得上 —— 改了版本忘了重建,
否则会得到一个「名字是新版、内容是旧版」的包,那种包装上手机才发现,比没有名字更糟。
(浮出来的默认产物 `build/app/outputs/flutter-apk/app-release.apk` 照旧保留:
`flutter install` / `run --release` 认的是它。)

**改名为什么在脚本里而不是 Gradle 里**:AGP 9 把 `VariantOutput.outputFileName`
从公开 API 拿掉了(只剩 `versionCode` / `versionName`),照旧写法编译不过,
要用得伸进内部实现 —— 而本仓库的约定本来就是「统一从这个脚本出入」。

**每做一次代码工作,`pubspec.yaml` 的 patch 与 `versionCode` 各 +1**
(`1.0.17+18` → `1.0.18+19`),这样产物名与安装包的版本永远对得上,也方便回滚比对。

这台开发机**直连 Google 系主机不通**(`services.gradle.org` 超时、
`maven.google.com` 无响应、`download.flutter.io` 连上但零吞吐),
所以三项镜像配置已经写进仓库,新环境克隆下来即可构建:

| 目标 | 处置 |
| --- | --- |
| Gradle 发行包 | `android/gradle/wrapper/gradle-wrapper.properties` → 腾讯镜像 |
| Maven 仓库(AGP / AndroidX) | `android/settings.gradle.kts`、`android/build.gradle.kts` → 阿里云前置,上游兜底 |
| Flutter 引擎产物 | `tool/build.sh` 设 `FLUTTER_STORAGE_BASE_URL=https://storage.flutter-io.cn` |

来的**(曲目 id + 档位 → 路径,没有索引文件,所以不存在「索引说有、盘上没有」),

排序那部分:口径换算与排序本身是纯函数(`sorting_test.dart`),状态层那几条

写操作同理:`write_operations_test.dart` 钉住线上形态(端点与参数名),
`playlist_writes_live_test.dart` 在真服务器上建一条**自检用**的歌单,
加歌 → 改名 → 按位置移除 → 删掉(只碰它自己建的那一条)。

### 性能姿态(为什么这么写)

下面几处看着「绕」,但都是为了性能 —— 别顺手改回去:

- **大列表一律是真懒加载**:音乐库的专辑网格 / 艺人栏、专辑页与搜索页的曲目都用
  sliver(`SliverGrid` / `SliverList.builder`)。**不要**换成嵌在 ListView 里的
  `GridView(shrinkWrap: true)` —— 那为了量自己的高度会把每一格都建出来:
  库里 400 多张专辑就是 400 多个卡片、400 多次封面解码,全压在进库那一帧。
- **播放位置单独一条通道**(`PlaybackController.position`),不进 `state` 的通知:
  位置每秒变好几次,混进去等于让整个可见界面跟着重建。
- **封面按显示尺寸解码**(`Cover` 里取 2 的幂做桶),并走磁盘缓存
  (`configureCoverCache`)。缓存键是「封面 id + 尺寸」而**不是 URL** ——
  Subsonic 每次请求换 salt,同一张图每次 URL 都不同。
- **新缓存只在「不花流量」的时候留**:听过的歌那份额度由播放触发,判据是设置页
  那个「仅 Wi-Fi 下载」开关 + 当前连接是否计费(`shouldWriteCache`)。**别把这层
  门控去掉** —— 留缓存等于在后台把整首歌拉完,用户以为流量下没下东西其实下了。
  已经留着的照旧读本机(那是白拿的)。淘汰只在三个时刻发生:启动、**换歌**、调额度。
  换歌那次是会话中途唯一的算账时刻(一直放下去不会重建播放源),所以别把它挪到
  「拼播放源」那一头(那儿是**整个队列**一起拼的,标出来的「正在听」会是最后一首)。
  淘汰**按文件 mtime** —— 所以命中时要刷新它的时间,否则常听的反而先被扔;
  正在听的那一份永远跳过(删掉它等于掐断当前这首的声音)。
- **缓存目录与下载目录是两处**(`media_cache` vs `download_store`)。
  别把缓存塞进 `Nordic/Music`:那是用户看得见、点名要的地盘,
  混进去会让「清缓存」看起来删掉了他的东西。
- **首页那几条货架是服务器口径,一次并行取三条**(`getAlbumList2` 的 newest /
  recent / frequent):「最近播放 / 最常播放」本地算不出来,只有服务器有播放统计。
  它们与整库那一栏**同一个端点**,所以是并行发出去、一起成功或失败 ——
  多这两条不会让启动那一轮变脆。三条都进了 `LibrarySnapshot` 并一起落盘,
  断网冷启动时首页照样有东西(见 `app_state_test` 的「缓存往返」)。
- **「全部歌曲」是按需翻页的,别改成一次取完**:一页 1000 首
  (`AppState._songPageSize`)。**500 不是这台 Navidrome 的上限** ——
  旧注释写「实测卡在 500」是误判,换成 `songCount=1000/2000/20000` 都返回全量。
  启动只拉第一页
  (全拉完在大库上就是几十个往返压在启动路径上),滚到底自动接着取
  (`AppState.loadMoreSongs`),页脚照实说「已取到 N 首 / 库里 M 首」。原先只铺第一页
  且页脚只报本地条数 —— 531 首的库上就是**默默少 31 首**。
  翻页那一页并上来时要**按 id 去重 + 按当前口径重排**(`mergeSongPage`):翻页期间
  服务器上增删会让页与页重叠,而偏移量在那种时候本来就不可靠。
- **短列表按内容撑高、长列表懒加载**(队列面板 / 下载里的曲目表,40 行为界):
  从一张五百首的专辑开播时,一次建五百行是能看出来的卡。
- **播放页 ↔ 歌词页不走过渡**(`AppRoutes.flip`):它们是同一个播放对象的两面,
  位移会读成「进了另一个页面」。专辑 / 艺人 / 歌单仍是滑入。
- **共享元素过渡的起点只在「屏幕上那一屏」里找**:主壳每个 tab 外面包了一层
  `HeroMode(enabled: tab == _tab)`(`shell.dart`)。框架是按 tag 在**整个来源路由**
  里找起点的、**不看元素在不在屏幕上**(`heroes.dart` 的 `_allHeroesFor` 只认
  `HeroMode`),而 `IndexedStack` 会把逛过的 tab **整棵保活** —— 少了这一层,
  「在首页点一张专辑 / 点播放坞」时起点会被音乐库那张**看不见的专辑网格**偷走:
  封面从屏幕外飞进来,而且每帧都在一个**变化的矩形**里重画(含 38px 的投影)、
  按新约束重算解码桶,正好落在滑入动画上 —— 2026-10-17 真机反馈的「点坞 / 返回
  卡顿」就是它(进 320ms、出 260ms 各一次,所以两个方向都卡)。
- **播放页不在共享元素过渡里**(`player_screen.dart` 那颗封面只是一张 `Cover`)。
  原型的起点是**从被点的那个元素**上取的(`prototype/app.js` 的
  `t.closest('[data-morph]')`),坞与歌曲行都不带 `data-morph` —— 点坞进播放页
  那一程原型**故意不飞**(「那块的尺寸太小,飞过去的观感不如不加」)。
  网格 → 专辑页那条仍在,别顺手一起去掉。
- **已知、本轮不动**:首页货架那两个 `Hero` 的 tag 是 `cover-rail-{id}`,与专辑页的
  `cover-{id}` **永远匹配不上** —— 从货架点进专辑页因此从来没有飞行(而修好
  `HeroMode` 之前,飞的反而是那张看不见的网格)。要修得让专辑页同时接受两种 tag;
  把两条货架都改成 `cover-{id}` 会踩「同一路由里重名 Hero」的断言
  (同一张专辑同时出现在两条货架上就会中),不能图省事。
- 氛围背景那两层各自隔了 `RepaintBoundary`(它们对同一套配色是静态的),
  并且明说了 `isComplex/willChange` 让光栅缓存愿意缓存;下载进度播报有
  「差 0.5% 且间隔 250ms」两道闸。
- **`BackdropFilter` 只能收裸 `ImageFilter.blur`**:**真机实测**过 —— 原先按原型写的
  `ImageFilter.compose(blur + saturate 色矩阵)` 在 Android(Impeller)上不生效,
  表现是坞背后滚动过去的曲目文字**清晰可读**,毛玻璃等于没有(只有 80% 的填充色挡着)。
  换回裸模糊后立刻恢复。别为了那点饱和度再塞回组合过滤器。
- **歌词的滚动落点靠 `GlobalKey` + `Scrollable.ensureVisible(alignment: 0.5)`**,
  不要自己估每行高度(估过:与真实行高差 40%,误差累积到副歌就跑到屏幕外)。
  **而且每一行都得真的建出来**(歌词列走 `SingleChildScrollView` + `Column`,不是
  `ListView`):没建出来的行拿不到 `currentContext`,而 `ensureVisible` 正是靠它量位置
  —— 于是「当前句在屏幕外」时那一下永远是空放,表现就是「刚点进歌词页停在第一句」。
  `ListView(children:)` **也是懒的**(`SliverChildListDelegate` 只给视口附近建 Element),
  想用无限缓存区把它逼出来也不行:`ScrollCacheExtent.pixels(double.infinity)` 会让
  视口的语义矩形变成非有限值,框架直接断言。
- **弹层一律走 `showNordicSheet`**(`components.dart`),别直接调
  `showModalBottomSheet` —— 它替掉的两处默认值各修一个真机问题:
  框架默认那层 `Colors.black54` 会与 `NordicScrim` 叠成**两层黑**(而且纯黑不模糊);
  不写 `isScrollControlled: true` 时框架只给内容盒子屏幕高度的 9/16,
  蒙板就只盖住下半屏,上半屏剩一块没有模糊的纯黑。
- **循环是三态(顺序播放 / 列表循环 / 单曲循环)**,刻意比原型宽 —— 原型只有开关两态。
  别按原型把它改回两态。三态的状态来自 `player.loopModeStream` 那条**单独订阅**
  (`setLoopMode` 不发 playbackEvent,`playerStateStream` 又被 `.distinct()` 压在
  playing/processingState 上,从它派生的话灯永远不亮、而且开了关不掉)。
- **循环键只换图标与底色,不弹文案**(2026-10-17 按要求移除了那版 SnackBar:
  连点三下就是三条「顺序播放 / 列表循环 / 单曲循环」的横幅)。所以那层
  `selectFill` 底色**不能省** —— 列表循环与顺序播放共用一个图标,少了底色这两个
  状态在屏幕上就是同一张脸(`repeatKeyAppearance` 有测试钉着)。
- **可点元素一律走 `Pressable`**(`components.dart`),别再用裸 `GestureDetector`:
  原型的 `.icon-btn:active` / `.btn:active` / `.play-btn:active` 都是**按下去缩一下**,
  移植时整层漏掉了 —— 于是全应用按下去屏幕上什么都不动,手感上就是「这机器慢」。
  整行 / 整条那种大块面用 `pressedDecoration`(**手机上的「按」= 原型的 `:hover`**,
  取 `--fill-1`),缩放留给键与按钮。两处同族的警戒线:
  **不可点的图标键要压暗**(上一首 / 下一首到头了那颗,不压暗就跟能点的一样,
  点下去什么也不发生 = 「这键坏了」);**行高用 `minHeight` 不用写死高度**
  (系统字号拉大时行要能跟着长高,写死会把文字裁掉半截)。
- **玻璃里的行不能用 `InkWell`**:涟漪画在最近那个 `Material` 的墨层上,而那一层
  在这张纸的玻璃**底下** —— 按下去屏幕上什么都不动(队列面板当初靠垫一层
  `Material(color: transparent)` 绕开,现已统一走 `Pressable` 的 `pressedDecoration`)。
- **服务器的入口有三处,别只留一处**:设置页的「服务器与线路」(前身「服务器」;
  右边明说点进去是什么,避免把「看线路」当成全部)、设置页的「添加服务器」
  (`openServers(form: true)` 直接落在表单上)、以及服务器页管理页里的
  **「服务器设置」**。第三处是 2026-10-17 补的:录入表单原先**只在「还没配过
  服务器」时出现**,于是连上之后再想改账号 / 密码 / 地址就没有路了 —— 那一屏
  只剩线路能改。表单从管理页进入时按钮是「保存并重新连接」、带一颗「取消」,
  存完自动退回管理页并弹一句回执。`connect()` 本来就是按「首次配置 / 修改配置」
  写的,`initState` 也早就把现有值(含密钥库里的密码)填回表单了。
- **改线路必须走 `SubsonicClient.setRoutes`**:客户端手上那份线路是**建库时拷贝的**,
  只改 `ServerConfig` 的话界面上的勾会动、请求却照旧走旧线路(真机报的「线路切换无效」
  就是这个)。生效线路一变还要把**正在放的那一首**重新装载 —— 流地址是装载时拼好的,
  不重载的话界面说「正在走新线路」而声音还在旧那条流里(`AppState.onRouteChanged`
  在 `main.dart` 接上 `PlaybackController.retargetRoute`,择优选速那条路也走这个钩子)。
  锁定是**单选**,且**再点一下锁定中的那条要能解除** —— 只有「锁」没有「解」的话,
  点错了就再也回不到自动择优。
- **时长要有兜底**:转码流的响应没有 `Content-Length`,平台(ExoPlayer / AVPlayer)
  报不出时长,只认 `durationStream` 的话进度条会**结构性**卡在 0(滑块还禁用拖动)。
  所以两处同时发力:播放源声明元数据时长(`ProgressiveAudioSource(duration:)`),
  换歌时再拿元数据铺一次(`PlaybackController._wire`),平台一旦报出真值就覆盖。

### 第三轮(2026-10-17):通知粒度与热路径上的盘操作

前两轮动的是「写法」(懒加载、独立通道、分桶解码);这一轮挖出来的是**通知的粒度**
与**热路径上的同步盘操作**。下面同样是「看着绕,别顺手改回去」:

- **只订阅真正读到的那几件,别 `watch` 整个 `AppState`**:`AppState` 把下载进度
  (最多每秒四次)与**音频缓存的淘汰**原样转发给全应用,于是「下载在跑」或
  「切了一首歌」会顺带把每一屏重建一遍。首页 / 音乐库 / 艺人 / 歌单 / 搜索改成
  `context.select` 挑自己读到的那几件(记录按**值**比较,那些事就到不了它们);
  根 `app.dart` 只 select 主题档位,两套 `ThemeData` 也缓存下来(`NordicTheme.light/dark`)
  —— `ColorScheme.fromSeed` 那趟调色计算不必每次通知重算两遍。设置页 / 下载页 /
  缓存面板**继续 watch**:它们真的在画进度与占用。守卫在
  `test/ui/rebuild_scope_test.dart`,一条规则两面都钉住 —— 进度跳动不许重建,
  真正订阅的东西变了必须重建。
- **`MediaCache` 只在数字真的变了的时候播报**:这一趟挂在**每次换歌**的淘汰上
  (`markPlaying` → `_pruneAfterTrackChange`),无条件播报等于让每次切歌都重建界面。
- **切歌那一下的淘汰不再每首都扫目录**:整个缓存目录 stat 一遍、几百份文件,是能
  感觉到的同步 I/O,而绝大多数换歌压根不会越过上限。真扫只在四种情况发生:缓存关着、
  **账面上已经超了上限**、有新文件可能落盘(`fileFor` 拿过空位)、距上次扫描超过
  15s(`MediaCache.rescanInterval`)。三条老约定一条没松:**淘汰仍然发生在换歌这一下**、
  LRU 仍按文件 mtime、正在听的那一份仍然跳过。`prune()` 本身仍是**全量**
  (启动 / 调额度 / 清空 / 测试都走它),而且一趟 `_scan` 同时产出占用与 mtime 序 ——
  原先淘汰要把整个目录 stat 两遍。
- **音乐库快照是合并写**:后台补齐每翻一页都要写一次,而每次都要把**整份**快照
  编码 + fsync,载荷越写越大 —— 合起来是平方级的活。`LibraryCache.write` 同一时刻
  只留一个写者,写着的时候又来的新版本**只留最新那份**;`settle()` 是「等它落定」,
  清缓存 / 删目录之前必须调(`clear()` 自己会等),否则 Windows 上就是
  「另一个程序正在使用此文件」—— 测试的 tearDown 也要等。`loadMoreSongs` 因此不再
  await 写盘,而 `loadLibrary` 继续 await:那条硬约定是「await 过之后读同一份缓存
  一定读得到刚取回的库」。
- **播放地址与缓存槽位都有备忘录**(`SubsonicRepository._rememberUri` /
  `MediaCache._slotFor`):一次 `setQueue` 会把**整条队列**的播放源都拼出来,上千首
  就是上千次「新生成盐 + MD5」外加两次 SHA-1,而其中绝大多数地址到播完也不会被请求
  一次。键里带**线路的 url**(不只是 id):地址被改掉而 id 不变时,只按 id 作键会把
  旧主机一直喂回去。未命中时照旧当场新生成盐 —— 协议口径没动,省的是那几千次哈希。
  下载索引那张封面表(coverArtId → 路径)同理**预先摊平**:它原先在**每个可见封面
  每次重建**时都遍历一遍所有下载记录。
- **冷启动不再数缓存目录**:`MediaCache.open(scan: false)` + 首帧之后
  `mediaCache.prime()`。那是整个缓存目录的 stat 遍历,而它要产出的三件东西
  (设置页的占用数字、清掉没主的半截文件、按上限淘汰)没有一件急着在首帧之前知道。
  **但 `loadCachedLibrary()` 仍然在 `runApp` 之前 await** ——「首屏就有东西」是这一屏
  的契约,改成先出空态是能被看见的。
- **播放页那张封面留旧帧**(`Cover(gaplessPlayback: true)`):换歌就是换图,新图解码
  要几十毫秒,不留旧帧的话每次切歌都先闪一下渐变兜底。原型是浏览器画的,本来就把上
  一张一直画到新图解码完 —— 这是向原型对齐,不是改设计。
- **坞那条玻璃隔了 `RepaintBoundary`**,切 tab 那 220ms 的淡入也隔了一层
  (`shell.dart`):透明度每变一帧就会把整屏重画一遍(包括首页那层 62px 的氛围模糊)。
  透明度、时长、缓动一个字没改,只是让它合成一张现成的层。
- **考虑过、这一轮没做**(写在案,免得下次重新发现一遍,也免得顺手「补」上):
  把快照编解码挪进 Isolate(载荷要跨 isolate 深拷贝一趟,省下的计算与那份拷贝
  成本相当,而重复编码已经被合并写消掉了)、给 `NetworkProbe` 加几秒 TTL(几毫秒的
  收益,换来「网络性质变陈旧」——「流量下不缓存」那道闸比它值钱)、给 `pingAll`
  加 TTL(它本来就并发且稀少,而陈旧排序会削弱「刚失败之后换线」这件事)、
  `songsByArtist` 并发翻页(要拿 500 一页去预取,小库上会**多发**请求,而它只在
  「下载整位艺人」时走)、`mergeSongPage` 跨页复用 id 集合(每页省的是 O(n),主项是
  它上面那次 O(n log n) 重排;动了还要冒「集合不同步 → 列表出重复行」的险)、
  下载队列那条面板改懒加载(那圈边框 + 分隔线是**一整块**面板,拆成每行一张卡片
  就是视觉改动,得先过 `prototype/`;而队列是几十条,不是几千条)。
  **服务器页 / 线路面板 / 添加线路三屏也仍是 `watch`**:它们是冷屏,重建的是一张
  静态表单,不值得为它冒「select 漏字段」的险。

### 第四轮(2026-10-17):进度跳转、歌词点句、放完不切歌

这一轮补的两件事都是**手动调进度**(拖进度条 / 点歌词),外加两处歌词页的老毛病。
第一条尤其值得记住 —— 它不是代码写法问题,是服务器给的东西**根本不能 seek**:

- **冷转码流不可 seek,所以「拖进度条」在远端曲目上要绕一圈**(`audio_handler` 的
  `_seekRemote`)。**实测**(Navidrome 0.64,`curl -D -`):
  - 一首**还没转码过**的曲子,`stream.view?maxBitRate=192&format=mp3` 回的是
    `Accept-Ranges: none` + `Transfer-Encoding: chunked` —— **没有长度、不支持 Range**。
    just_audio 的流式源于是交给平台一个「无长度、不可 seek」的源,`player.seek()`
    **静默不做**:用户看到的就是「拖了,进度纹丝不动」。
  - 同一个 URL 一旦服务器的转码结果落成静态文件,回的就是
    `206 + Content-Range + Accept-Ranges: bytes`(带全长)—— **那才是能 seek 的**。
    本机那一份(下载的 / 边听边缓存下完的)同理。
  - 所以 `seek` 分两步:正在放的是**本机那一份**(装载那一刻记下的,不是此刻磁盘上有没有
    —— 半路下完并不会换掉正在放的那条流)就直接交给平台;是远端流就**等本机那份下完**
    (局域网上一首 3 分钟的歌不到 5 秒,上限 8 秒),再整批重载到目标位置
    (`_reloadAt`,与切档位同一套)。等不到就退回平台的原生 seek —— 那一下在冷流上不作数,
    但**不会把歌从头重放**,也不假报进度。
  - **缓存关掉 + 远端曲目**因此仍然跳不动(没有「本机那一份」可等),这是已知边界:
    「不缓存」就是「每次从服务器拉一条流」,而那条流本来就没有长度。
- **松手之后拇指停在落点上**(`scrubberHold`):远端那一下 seek 要等几秒才落地,
  这期间位置还是旧的 —— 拇指立刻弹回去,看着就像白拖了。两条退出口都必要:
  位置追上了(`settle`)、或者等够久了(`giveUp`,那一下确实没生效)。
- **点某一句歌词 = 跳到那一段**(`seekTargetForLine`);**点行以外的空白仍是回封面**
  —— 与「点封面看歌词」互为来路的那一条不能丢。有时间轴就跳那一句的起点;没有时间轴
  只能按整首摊行反推,取**那一行的中段**而不是起点:高亮走的是
  `floor(比例 × 行数)`,起点在浮点误差下会退到上一行(点第三句、高亮停第二句)。
  两者互为逆运算,有测试钉着(`test/app_test.dart` 的「点一句 → 高亮必须落回同一行」)。
  跳不到的地方(没时间轴又不知道时长)返回 `null`,界面**不接这一下点击** ——
  跳不到的地方不该装成跳了。
- **歌词页的重建面收在「换行那两行」**:当前高亮行是一条 `ValueNotifier`,
  每行自己订它、自己判断要不要重建(`_LyricLine` 的 `_stateFor`)。原先换一行是
  **整屏 + 上百行**重建一次,而且正好落在自动滚动那 260ms 的动画里 ——
  真机反馈的「跳转动画一顿一顿」多半就是这几帧。写「已经排过滚动」的那本账
  (`_scheduledFor`)也一样:同一行只排一次,排重了就是好几个 `ensureVisible`
  同时开跑、互相打断。
- **放完一首后「自己重头再放一遍」是平台干的,护栏在应用这一侧**
  (`audio_handler` 的位置监察 + [didPlatformRewind])。真机抓到的现场(2026-10-17,
  多首队列、熄屏、蓝牙耳机):
  - 一首**还没转码过**的曲子(源是 `lockcache`,即那条 `Accept-Ranges: none` +
    chunked 的**无长度冷流**)放完时,平台**没有切下一首**,而是把**这一首**从 0 秒
    又放了一遍 —— 用户读到的就是「后台播放单曲循环,不会自动切下一首」。
  - 同一首换成**本机文件**(上一轮已经缓存下来的那一份)再放,末尾就老老实实停住了。
    **差别只在源上:有没有长度。** 另外**队列里只有一首**时末尾停住也是对的
    (没有下一首可切),别把那个当成同一个 bug。
  - Dart 侧全程**既没收到 `completed`、也没收到暂停**(逐条日志验证过),也就是说
    just_audio 里「正常那一支」(末尾 `seekToNextMediaItem`)压根没走到 —— 所以
    「在 `completed` 时补一刀」这种修法**不会生效**(那一支不触发)。
  - 于是自己在**位置流**上盯:位置没来由地往回跳一大截 = 平台又倒回开头了 → 自己
    `seekToNext()` 接着放(队列到头就按「这一轮放完」处理)。判据缺一不可
    (我们请求过的 seek、换歌、单曲循环、小抖动都不许误判),有测试钉着
    (`test/playback/playback_test.dart` 的「平台倒回开头」)。那条日志
    「`[Nordic] 平台倒回开头 → 自己切下一首 idx=…`」在真机上**正好在每个曲子末尾
    各出现一次、全程无误触发** —— 它现在是**常驻**的一行(`debugPrint`):
    冷流上这条护栏是**唯一在切歌的那一支**,下一轮真机还要靠它判断有没有响。
  - **平台内部为什么这么干仍是推测**(时长未知时那条末尾恢复分支?媒体期重新预备?),
    证据只到「它把这一首原地重放了」这一步 —— 文档里别把它升级成定论。
- **补强(2026-10-18)**:上面那条护栏补了四处,都是它自己的洞:
  - **门槛跟着曲长收**(`didPlatformRewind` 多了 `trackDuration`):写死「至少 10 秒」
    的话,间奏 / 试听片段这类十秒以内的曲子位置永远够不着门槛 —— 护栏在最需要它
    的那一类曲子上等于不存在,结果是一直单曲循环。
  - **暂停期间那一跳要留住**:位置监察原先先更新基线、再判断「没在播放就返回」,
    于是平台趁暂停倒回开头时那一下被记成了新基线,用户一按播放还是同一首从 0 开始
    —— 原症状换个场景原样复发。现在暂停期间两个基线都不动(下标也不动:否则暂停
    期间换过歌、基线跟着走,恢复播放时会读出「位置跳了但下标没变」的假阳性,
    反而多切一首)。
  - **队列走到头要真的按住播放器**:那一支原先只播报「放完了」,没碰播放器 ——
    平台还在重放,于是界面说放完、扬声器还在响。
  - **真切之前再核一遍**(下标没变 + 位置仍在开头附近):判据到动手之间隔着一次
    异步,平台在**有长度**的源上本来也会自己切,两边各切一刀就是**跳过一整首**。
  - 这条护栏现在有**处理器级**测试:测试里给 `NordicAudioHandler` 递一个可摆布的
    播放器(`_FakePlayer` 继承真 `AudioPlayer`,在测试环境里它是惰性的),
    摆布位置流就能钉住「切一次 / 换歌不算 / 拖动不算 / 单曲循环不算 / 暂停期间
    留住那一跳 / 不在开头附近就不动 / 队列尽头要按住」。只测纯函数是不够的 ——
    冷流上切歌全靠它。
- **考虑过、这一轮没做**:歌词列外面那层 `ShaderMask`(原型 `.lyrics` 的
  `mask-image`,边缘渐隐)在滚动时每帧都要重做一次**整块离屏合成**,是上面那条修完
  之后剩下的头号嫌疑。之所以没动它:渐隐是渐到**氛围背景**上(那层有光晕),换成
  「盖一条背景色渐变」就是改设计(得先过 `prototype/`),而这一轮已经能靠收窄重建面
  把工作量降下来。真机上要是还卡,下一刀在这里。

### 第五轮(2026-10-18):缓冲进度、缓存只留最高档、播放页多两处歌词入口

- **进度条多一段「已缓冲」**(`playback_controls.dart` 的 `_BufferedTrackShape`)。
  缓冲位置走**单独一条通道**(`PlaybackController.buffered`)—— 与 `position` 同一套
  待遇:它来自同一条 `playbackEventStream`,远端流上每秒动好几次,混进 `state` 等于
  让每一屏跟着重建(换歌时先归零,免得上一首的缓冲带在新歌上闪一帧)。画法上只重写
  `paint`:自己画底与缓冲带,再把父类的 inactive 调成透明后调它 —— 父类会把未加载段
  从拇指往右**整个重画一遍**,那一下正好把缓冲带擦掉。**手势仍归 `Slider`**,拖动 /
  松手落点 / 「时长未知不给拖」一个字没动。「画不画」的四条口径(时长未知 / 整首都在
  手边 / 没跑到播放位置前 / 越界夹回)全落在纯函数 `scrubberFrame` 里,于是能直接测;
  不画时连绘制路径都换回原来那条 —— 本机文件那一支与改动前一样。缓冲带用中性的
  `fill3`:强调色是「播到哪儿」的专用信号,让它同时管两件事,这两段就分不出来了。
- **同一首的缓存只留最高那一档**。缓存路径是「曲目 id + 档位」算出来的,于是同一首在
  192 与 原音 各留一份**永远并存**、额度白占。两边一起治:
  - **读**:本机已有**更高**一档的完整缓存时直接拿它播 —— 白拿的音质、不花流量,而且
    这一首压根不会再写第二份(`fileFor` 都轮不上)。候选按「从高到低」给
    (`quality.dart` 的 `betterTiersThan`),**只要完整的**(半截的播到一半会断)。
  - **写**:更高档那份**完整落到本机之后**,同曲更低档那几份让位(连 `.mime` 旁注
    一起删,占用账跟着降)。两条护栏缺一不可:**高码率那份还在下(只有 `.part`)** 时
    一个都不删 —— 网络一断两头落空;候选路径**纯算**、最多三下 stat、**不扫目录**
    (这一步挂在每次换歌上,不能变贵)。
  - 顺带把 `_localLoaded` 从「是不是本机文件」扩成「哪一份 / 哪一档 / 哪个路径」:
    本机拿更高档那份播时,照**所选档**去算缓存路径会指到一个**不存在**的文件 ——
    `_playingPath` 指错,淘汰时就可能删掉正在解码的那一份。
- **播放页的歌词入口从「封面那一块」扩成「整块封面区 + 歌名」**。原先封面四周那一大圈
  留白按下去什么也不发生,而这一屏除了控件就没有别的去处了。艺人 / 专辑那两条链接与
  进度条拖动照旧不受影响(原型那头的委托按 `closest()` 走,**最近的 `data-*` 先赢**)。

### 已知环境问题

开发机上的 AVD `nordic-ui-api34` 网络配置有缺陷:`eth0` 是
`inet 10.0.2.15/8`,`/8` 掩码把 `192.168.10.4` 判成同网段,于是不走网关、
LAN 流量被错误路由(现象是 TCP 能握手但收不到任何字节)。无 root 改不了
路由表,**所以在这个模拟器上无法验证真实音频播放**。要验音频请用真机。
